Fresh Grape Traceability PoC
Remix 部署与手动测试说明

============================================================
一、建议的测试环境
============================================================

第一次测试建议使用 Remix VM，不要先使用 Sepolia。

原因：
1. Remix VM 自带多个测试账户和测试 ETH。
2. 可以很方便地切换 Administrator、Regulator、Producer、
   Transporter、Retailer 和未授权用户。
3. 交易确认快，失败交易也不会浪费真实测试币。

Remix 网站：
https://remix.ethereum.org/

============================================================
二、创建和编译合约
============================================================

1. 在 Remix 左侧 File Explorer 中创建 contracts 文件夹。
2. 在 contracts 文件夹中创建：
   - ActorRegistry.sol
   - GrapeTraceability.sol
3. 把项目中对应合约的完整代码分别粘贴进去。
4. 确保两个文件位于同一个 contracts 文件夹中，因为
   GrapeTraceability.sol 使用以下相对路径：

   import {ActorRegistry} from "./ActorRegistry.sol";

5. 打开 Solidity Compiler。
6. Compiler 选择 0.8.28。
7. 编译 ActorRegistry.sol。
8. 编译 GrapeTraceability.sol。
9. 如果底部显示绿色勾号并且没有红色错误，说明编译成功。

============================================================
三、账户和枚举数字
============================================================

打开 Deploy & Run Transactions，把 Environment 选择为：

Remix VM (Cancun)

记录前六个 Account 地址，并按以下方式分配：

Account 0 = Administrator
Account 1 = Regulator
Account 2 = Producer
Account 3 = Transporter
Account 4 = Retailer
Account 5 = Outsider（未注册用户）

每次调用函数前，一定要检查当前选择的 Account。

Role 数字：
0 = None
1 = Administrator
2 = Producer
3 = Transporter
4 = Retailer
5 = Regulator

BatchStatus 数字：
0 = None
1 = Created
2 = InTransit
3 = Delivered
4 = Flagged
5 = Recalled

QualityType 数字：
0 = TemperatureSummary
1 = Inspection
2 = Delivery

============================================================
五、部署两个合约
============================================================

步骤 1：部署 ActorRegistry

1. Account 选择 Account 0。
2. Contract 选择 ActorRegistry。
3. 点击 Deploy。
4. 在 Deployed Contracts 中展开 ActorRegistry。
5. 调用 systemAdministrator。

预期结果：
返回 Account 0 的地址。

步骤 2：部署 GrapeTraceability

1. 复制刚才部署的 ActorRegistry 合约地址。
2. Contract 选择 GrapeTraceability。
3. 在 actorRegistryAddress 输入 ActorRegistry 合约地址。
4. 点击 Deploy。
5. 展开 GrapeTraceability，调用 actorRegistry。

预期结果：
返回刚才部署的 ActorRegistry 合约地址。

错误部署示例：
如果把 Account 0 的钱包地址，而不是 ActorRegistry 合约地址填入
actorRegistryAddress，部署应该失败并显示 InvalidActorRegistry。

六、注册五种参与者
============================================================

下面的 registerActor 都在 ActorRegistry 合约中调用。

步骤 1：Administrator 注册 Regulator

当前 Account：Account 0
函数：registerActor
account：Account 1 的地址
role：5

预期结果：
交易成功，并产生 ActorRegistered 事件。

步骤 2：Regulator 注册三个业务参与者

切换当前 Account：Account 1

调用 1：
account：Account 2 的地址
role：2

调用 2：
account：Account 3 的地址
role：3

调用 3：
account：Account 4 的地址
role：4

预期结果：
三次交易都成功，并产生 ActorRegistered 事件。

检查方法：

在 ActorRegistry 中调用：

getActor(Account 2 地址)
hasRole(Account 2 地址, 2)
isActive(Account 2 地址)

预期：
role = 2，active = true，hasRole = true。

七、经典示例 1：完整正常追踪和召回流程
============================================================

步骤 1：Producer 创建葡萄批次

当前 Account：Account 2
合约：GrapeTraceability
函数：createBatch

externalId：
GRAPE-REMIX-001

productType：
Fresh table grapes

harvestDate：
1750000000

1750000000 是过去的 Unix 时间戳。不能填写 0，也不能填写未来时间。

预期结果：
产生 BatchCreated 事件。

调用以下 view 函数检查：

getBatchByExternalId(GRAPE-REMIX-001)

预期：
- producer 是 Account 2
- currentCustodian 是 Account 2
- transferCount = 0
- qualityRecordCount = 0
- status = 1（Created）

步骤 2：取得 batch key

调用：
batchKey(GRAPE-REMIX-001)

复制返回的 bytes32 key。后面的交易都需要使用这个 key。

步骤 3：Producer 转移给 Transporter

当前 Account：Account 2
函数：transferCustody

key：
上一步返回的 batch key

newCustodian：
Account 3 的地址

deliveryEvidenceHash：
PICKUP_HASH

预期：
- 产生 CustodyTransferred 事件
- currentCustodian 变成 Account 3
- status = 2（InTransit）
- transferCount = 1

步骤 4：Transporter 添加温度质量记录

当前 Account：Account 3
函数：addQualityRecord

批次 key

recordType：
0

TEMPERATURE_EVIDENCE_HASH

summaryHash：
TEMPERATURE_SUMMARY_HASH

uri：
offchain://temperature/GRAPE-REMIX-001

thresholdBreached：
false

预期：
- 产生 QualityAdded 事件
- qualityRecordCount = 1
- status 仍然是 2（InTransit）

步骤 5：Transporter 转移给 Retailer

当前 Account：Account 3
函数：transferCustody

key：
批次 key

newCustodian：
Account 4 的地址

deliveryEvidenceHash：
DELIVERY_HASH

- transferCount = 2

步骤 6：Retailer 添加检查记录

八、经典示例 2：温度超标后自动 Flagged
============================================================

使用新的 externalId，避免与前一个批次重复。

步骤 1：
Account 2 调用 createBatch：

externalId：GRAPE-REMIX-002
productType：Fresh table grapes
harvestDate：1750000000

步骤 2：
调用 batchKey(GRAPE-REMIX-002)，复制新 key。

步骤 3：
Account 2 调用 transferCustody，把批次转给 Account 3。

步骤 4：
Account 3 调用 addQualityRecord：

key：新 key
recordType：0
evidenceHash：TEMPERATURE_EVIDENCE_HASH
summaryHash：TEMPERATURE_SUMMARY_HASH
uri：offchain://temperature/GRAPE-REMIX-002
thresholdBreached：true

预期：
- 产生 QualityAdded 事件
- 同时产生 BatchFlagged 事件
- status 自动变成 4（Flagged）

步骤 5：
Account 3 尝试调用 transferCustody，把批次转给 Account 4。

预期：
交易失败，错误为 BatchLocked。

这个例子展示了 oracle 报告温度超标后，智能合约会执行真正的业务逻辑，
自动锁定批次，而不是只保存数据。

九、经典示例 3：权限和非法流程测试
============================================================

例子 1：未注册用户创建批次

当前 Account：Account 5
调用 createBatch。

预期：
失败，错误为 RequiredRole。

例子 2：Regulator 尝试创建 Administrator

当前 Account：Account 1
在 ActorRegistry 中调用：

registerActor(Account 5 地址, 1)

预期：
失败，错误为 RoleAssignmentNotAllowed。

例子 3：Producer 跳过 Transporter

Account 2 创建新批次 GRAPE-REMIX-003，取得 key 后，直接调用：

transferCustody(key, Account 4 地址, DELIVERY_HASH)

预期：
失败，错误为 InvalidCustodyTransition。

例子 4：旧 custodian 添加质量记录

先由 Account 2 把 GRAPE-REMIX-003 正常转给 Account 3。
然后切回 Account 2 调用 addQualityRecord。

预期：
失败，错误为 NotQualityWriter。

例子 5：暂停参与者

1. Account 0 在 ActorRegistry 中调用：
   setActorActive(Account 3 地址, false)
2. Account 3 尝试转移当前持有的批次。

预期：
失败，错误为 ActorNotActive。

测试完成后，Account 0 可以调用：

setActorActive(Account 3 地址, true)

恢复 Transporter。

============================================================
十、在 Remix 中查看事件和错误
============================================================

1. 成功交易后，查看 Remix 底部 Terminal。
2. 展开绿色交易记录。
3. 在 logs 中可以看到：
   - ActorRegistered
   - BatchCreated
   - CustodyTransferred
   - QualityAdded
   - BatchFlagged
   - BatchRecalled
4. 失败交易通常显示为红色。
5. 展开失败交易，可以看到 custom error 名称，例如：
   - RequiredRole
   - InvalidCustodyTransition
   - NotQualityWriter
   - BatchLocked
   - InvalidActorRegistry

失败交易不会修改合约状态。

============================================================
十一、改用 Sepolia 时
============================================================

本地 Remix VM 全部测试成功后，再测试 Sepolia：

1. MetaMask 切换到 Sepolia。
2. 准备有 Sepolia ETH 的测试钱包。
3. Remix Environment 选择 Injected Provider - MetaMask。
4. 按相同顺序部署 ActorRegistry 和 GrapeTraceability。
5. 保存两个真正的 Sepolia 合约地址。
6. 把地址写入项目的 addresses.txt。
7. 在 Sepolia Explorer 查看部署交易和事件。

如果要完整模拟五个角色，需要准备多个 MetaMask 测试账户。
不要把钱包私钥粘贴到 Remix 文件、GitHub、PPT 或 addresses.txt 中。
